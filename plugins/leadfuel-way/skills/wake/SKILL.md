# wake (one watcher pass)

The owner clicks a card on the Router desk page, and before this nothing woke the router: he typed "answered" in its chat. This pass replaces that typing. It runs in a scheduled task of its own (`wake-on-answer`, Haiku, every 15 minutes), because only a Claude session can read the page's database and send a session a message, a session cannot message itself (measured: "refusing to send a message to the current session"), and a router that polled would spend a full-context turn on every tick. A plugin hook cannot do it (hooks fire only inside a session that is already running, and cannot call ArtifactData), nor can a plain local script (the page's database and session messaging are reachable only through Claude's tools).

**Four states, one pass.** `DELIVERED` only when the target's own transcript holds the card's token. A send that was queued or held for approval is `HELD` and is rechecked next pass, never resent. A failed send, or HELD or UNKNOWN past 120 minutes, is `UNDELIVERED` and gets a durable note on the Build Board. A pass that cannot read its inputs says `UNKNOWN`. A send is not delivered because it was sent.

**UNDELIVERED is retried (0.1.26).** Measured 2026-11-23: 84 unrouted cards sat UNDELIVERED for good. 47 had gone to an asker that is now archived (21 of them already archived when the send went out), 18 to a session id no store row has (17 real, one the withdrawn proof card), and 19 to a live session that never started on the message (queued, or "no sign of starting within 20s", which the tool says it "can still pick up later", now read as a hold). The plan now sends an UNDELIVERED answer again, at most 3 tries in all (`wake.attempts`): at once when the send said the target is archived or not found (`wake.gone`), else 60 minutes after the last try. A retry never goes to a target known to be gone (archived in the session store, or named in `wake.gone_to`); it goes to the asker's live successor: the highest live router of the project the asker's title names (`NODE · novah estate part · 10` finds `ROUTER #140 · novah estate`, and a bare `ROUTER #102` finds its project through the archived #102's own title), the one live upper-case `CONDUCTOR` for a conductor's card, else `router/current` when that is not archived. The 48-hour rule does not apply to a retry (the answer was tried and never arrived); a retry older than 30 days is listed as `retry_too_old` and left. The message says which cards are sent again, so the reader checks the card before acting.

## The pass
Pages: Router desk `https://claude.ai/artifact/LzmP6QcxmYh9TdvMMjS883` (collection `questions`); Build Board `https://claude.ai/artifact/A4uS9xn1emqupohdE4DUfV` (collection `router`). Script: `python "${CLAUDE_PLUGIN_ROOT}/scripts/wake_on_answer.py"`. Use PowerShell for any shell step (a scheduled run's Bash may lack tools on PATH).

1. **Tools**, one ToolSearch: `select:ArtifactData,mcp__ccd_session_mgmt__get_session,mcp__ccd_session_mgmt__send_message,mcp__ccd_session_mgmt__search_session_transcripts,mcp__ccd_session_mgmt__archive_session,mcp__scheduled-tasks__list_task_runs,mcp__ccd_session_mgmt__get_usage`.
2. **Self.** `get_session` with `self`: note your id S. The scheduled task runs in `auto` mode and that is expected (the routine's mode is set in the app and no session may change it): go on in `auto` or `bypassPermissions`. Only `default`, `acceptEdits` or `plan` stop the pass, with `WAKE-PASS UNKNOWN: not in auto or Bypass (mode=<mode>)` and nothing else done: a run in default mode cannot send (measured 2026-10-13), its send would wait for an approval nobody gives. **Until 0.1.15 this step also stopped `auto`, on an inference that was never measured; 11 passes in a row (2026-10-31) did nothing for that reason while 38 answered cards sat unrouted.** A send that `auto` refuses or holds is not a reason to stop: it is a result. Write the tool's whole text to `sent\<token>.txt` as step 7 says and let the judge call it HELD or UNDELIVERED.
3. **A fresh folder** W, new for this pass: `$env:TEMP\wake-on-answer\<UTC yyyyMMddTHHmmss>`, with `work\sent` and `work\seen` inside. Never reuse one: the script counts files.
4. **Read the cards.** ArtifactData `query` on the Router desk, collection `questions`, query `{"where": [["routed", "==", null]], "limit": 500}`, `out_dir` W\cards. The page writes `routed: null` on every answer and every note, so this is exactly the unrouted set (measured 2026-10-14: 23 cards, the answered census cards among them). Note the count N the result reports and keep its lines: they carry each card's version. If the query fails, end with `WAKE-PASS UNKNOWN: cannot read the questions collection`.
5. **Read the live router.** ArtifactData `get` on the Build Board, collection `router`, doc `current`, `out_dir` W\board. Never read it inline: it is about 260 KB. Read it every pass: the router rotates (it did during the proof) and the script follows `session_id`.
6. **Plan.** `plan --cards W\cards\questions --count N --router-current W\board\router\current.json --sessions-dir "$env:APPDATA\Claude\claude-code-sessions" --self S --out W\plan.json`. The script reads the desktop app's own session folder to find the router a card's `asker` names (`ROUTER #114 · app brain link`), or its live successor in that project, because no card carries `asker_session` and `router/current` is one router for the whole estate (measured 2026-10-31: it named a retired router while twelve project routers were asking). Since 0.1.18 an asker that is exactly one live session's title (`WATCH · desk archival analysis part 2`) reaches that session, and **an asker that names `ROUTER #N` when the store is readable and no live router has that number or project is NO TARGET**: the card is judged UNDELIVERED with a note on the Build Board, and is never sent to `router/current` (measured 2026-10-31: that named a retired router of another project). A pass of 2026-11-01 00:08Z found that a send to an idle router came back `no sign of starting within 20s` four times out of five and none of the five messages was in any target's transcript 80 minutes later: treat `undelivered` as real, do not assume the text arrives late. It sends a card the owner answered more than 48 hours ago to nobody and lists it as `stale` (he relayed it by hand long ago), and it puts at most 10 cards and 7,000 characters in one message so that you can send the text unchanged; the rest wait for the next pass. It prints one `SEND` line per target (at most five), one `RECHECK` line per held or unknown card, a `PIN cards=…` line, or `WAKE-PASS nothing to deliver`; in that case go to step 9b (never skip 9b: an empty card queue says nothing about the Owner Walk). A `WARNING: no readable session store` line is not a failure: those cards went to the live router. `WAKE-PASS UNKNOWN` (exit 2): end with that line. Write `W\work\versions.json` as `{"<card id>": <version>}` for exactly the cards on the `PIN` line, from the step-4 lines.
7. **Send**, for each `SEND to=<id> token=<token> ... message=<file>`: Read the message file and send its text, unchanged, with `mcp__ccd_session_mgmt__send_message` to `<id>`. Write the tool's whole result, error text included, to `W\work\sent\<token>.txt`. Only after the send has returned, `search_session_transcripts` with query `<token>` and `limit` 10, and write its whole output to `W\work\seen\<token>.txt` (`No matching sessions found.` included). Never issue the two calls together: a search raced against its send finds nothing (measured), and the card waits a pass as UNKNOWN. Send nothing else to anyone.
8. **Recheck**, for each `RECHECK ... token=<token>`: `search_session_transcripts` with query `<token>`, output to `W\work\seen\<token>.txt`. Never resend.
9. **Judge and write.** `judge --plan W\plan.json --work W\work --out W\out`. Then one ArtifactData `batch` on the Router desk whose `writes` are the entries of `W\out\batch.json`, exactly as written (each points at a card file and is pinned with `if_version`; on a version conflict write nothing for that card: the next pass takes it again). If `W\out\fallback.json` is not `{}`: ArtifactData `get` Build Board `router/wake_undelivered` with `out_dir` (missing is fine), then `update` it with `file_path` W\out\fallback.json, pinned to the version you read (a `set` with no pin only when it did not exist).
9b. **Owner Walk** (0.1.27; owner to CONDUCTOR 061, 2026-11-23 PT: "each click is carried out automatically afterward"). The Owner Walk page `https://claude.ai/artifact/1i1FhsztHxTi16NYwYhpNL` writes each click as a row `walk/<id>` with `exec.state = queued`; this step carries the clicks out. Script: `python "${CLAUDE_PLUGIN_ROOT}/scripts/owner_walk.py"`; items: `F:\Claude Sessions\handoff\ROUTER-140\owner-walk\items.json` (if it is missing, end this step with `OWNER-WALK UNKNOWN: no items.json` and go on to step 10). Folder WW = W\walk.
   1. ArtifactData `list` on the page, collection `walk`, `query` `{"limit": 1000}`, `out_dir` WW\rows. Never list inline. Write WW\v1.json as `{"<row id>": <version>}` from the result lines, and note the count N. A failed list ends the step with `OWNER-WALK UNKNOWN: cannot read the walk rows`.
   2. `plan --items <items.json> --rows WW\rows --count N --versions WW\v1.json --sessions-dir "$env:APPDATA\Claude\claude-code-sessions" --router-current W\board\router\current.json --self S --already-sent <sends made in step 7> --out WW\plan`. `OWNER-WALK UNKNOWN` (exit 2) ends the step with that line; `OWNER-WALK nothing to do` goes to step 10.
   3. If WW\plan\running.json is not `[]`: one ArtifactData `batch` on the page whose `writes` are its entries, exactly as written. This marks each row `running` before anything is sent, and creates the row of a pre-decided item (unpinned, so the store refuses it when the owner's veto landed first). If the batch is refused, write nothing more, send nothing, and end the step with `OWNER-WALK HELD: running batch refused`; the next pass takes the rows again.
   4. For each `CARD walk=<id> card=<q>`: ArtifactData `get` on the Router desk, collection `questions`, doc `<q>`, `out_dir` WW\rd; write WW\rdv.json `{"<q>": <version>}`. Then `cards --plan WW\plan\plan.json --cards WW\rd\questions --versions WW\rdv.json --out WW\work`. If WW\work\card_batch.json is not `[]`: one ArtifactData `batch` on the Router desk with its entries, and write the tool's whole result text to WW\work\card_result.txt. The card's `routed: null` lets the next wake pass route the answer to the asker.
   5. For each `SEND to=<id> token=<t> ... message=<file>`: send the file's text unchanged with `mcp__ccd_session_mgmt__send_message`, write the whole result to WW\work\sent\<t>.txt, then (only after it returned) `search_session_transcripts` query `<t>`, limit 10, whole output to WW\work\seen\<t>.txt. For each `RECHECK ... token=<t>`: the search only. Never resend.
   6. ArtifactData `list` the `walk` rows again into WW\rows2 and write WW\v2.json from its lines (the running batch moved the versions). `judge --plan WW\plan\plan.json --work WW\work --versions WW\v2.json --out WW\out`, then one ArtifactData `batch` on the page with the entries of WW\out\batch.json, exactly as written. A version conflict writes nothing: the next pass takes the row again.
   **The guard is in the script, not in you.** `owner_walk.py` decides, and you never widen it: a row on an item that could spend, transmit or deploy (`law9: true`, the amber items) is carried out only on its separate amber Yes (`choice: yes` with `law9_yes.stated` non-empty and equal to the item's `law9_stated`); a Yes with no stated cost or recipient only asks an agent to find it read-only and the row ends `held`; "Do the default" there does only the inward parts; a plain click marked yes without the amber Yes is refused (`held`, nothing sent); a typed-yes or credential item is relayed and ends `held` with the owner's exact step. The pass never writes `done`: that is the owning desk's word, with its finish-line proof. A row is `relayed` only when the target's own transcript holds the token or the card write returned a version; a failed send is `failed`; anything the pass could not see is `unknown`. A row whose option is not one of the item's own, or whose time is not the page's format, is refused (`held`). A row this executor left `running` with no token (a pass that died) goes back to `queued` after 120 minutes. An amber Yes written onto a card carries its stated cost or recipient in the card's note. This step itself never deploys, mails, posts or pays: it writes rows and cards and sends messages to this machine's sessions.
10. **Tidy.** `list_task_runs` for `wake-on-answer`, `limit` 20. Archive each run that is not S, not archived, and has status `succeeded` or `failed` (never `running`), one at a time with `archive_session`. Never archive anything else.
10b. **Resume sweep** (0.1.20; owner, 2026-10-31: "i shouldnt have to keep approving things"). A session that died on a usage limit (`You've hit your weekly limit, resets 2pm (America/Tijuana)`) stays dead until someone types "keep going"; the owner typed it into about a dozen after the reset of 2026-10-31. After the Tidy step, call `get_usage` and write its whole JSON to `W\usage.json`; count the sends this pass made (step 7) as K; then `python "${CLAUDE_PLUGIN_ROOT}/scripts/resume_sweep.py" plan --sessions-dir "$env:APPDATA\Claude\claude-code-sessions" --usage W\usage.json --state "$env:LOCALAPPDATA\leadfuel-way\resume_sweep_state.json" --self S --already-sent K --out W\sweep.json`. It prints one `NUDGE to=<id>` per stranded session whose limit has reset and that nobody has touched since (store `error` matches "hit your .* limit", `lastActivityAt` no later than `errorAt` plus two minutes, not archived, not a run of another routine, `errorAt` within 72 hours), at most 8 and never more than the ten sends a session may make before messaging pauses (K counts), and only while `get_usage` shows no window at 100%. `RESUME-SWEEP FULL` or `UNKNOWN` means send nobody. For each `NUDGE`, `mcp__ccd_session_mgmt__send_message` to `<id>` with exactly `limit reset, keep going`; then `resume_sweep.py record --plan W\sweep.json --state <the same file> --sent <ids whose send did not return an error>`, so the cooldown (60 minutes, three nudges for one error) holds. A row it lists as unknown (reset time unreadable) is never nudged. Never change a permission mode; a send the app holds is a result, not a reason to retry.
11. **End** with the judge's last line (`WAKE-PASS DELIVERED=… HELD=… UNDELIVERED=… UNKNOWN=…`), or the step-6 line, then the Owner Walk line (`OWNER-WALK relayed=… held=… failed=… unknown=… running=… queued=…`, or its nothing / UNKNOWN line), then the sweep's last line (`RESUME-SWEEP nudge=...`). Ids and counts only. Count the step-9b sends in K for step 10b.

## What a card carries afterwards
- `wake`: `{state, at, to, why, delivery, message_id, first_sent_at, sends, attempts, gone, gone_to, answered_at, note_at, by}`. The token is never written to a card: a router reading the card would otherwise carry it in its own transcript and a message that never arrived would look delivered.
- `routed` (only when DELIVERED): `{at, by: "wake-on-answer", to, note}`. The page then shows the owner that his answer was picked up. The session that acts writes what it did in `routed.note`.
- A card the owner answers again, or adds a note to, gets `routed: null` from the page and a new `answered_at` or `note_at`, so the next pass sends it again.

## Who is the target
`asker_session` when it is a full `local_` id; else a full `local_` id inside the `asker` text; else the router or session the asker names by title; else the live router, `router/current.session_id` on the Build Board. Since 0.1.26 an id that is known gone (archived in the store, or a send said archived / not found) is skipped for the asker's live successor (section above). A row id such as `intelligence/local_8e471cfd-1` is not a session. A router that wants a desk woken directly puts that desk's id in `asker_session` when it posts the card, and only for a desk under 300k tokens (`leadfuel-way:router`, "Waking").

## Never
- Never change any session's permission mode to get a message through (the owner's standing rule). A held message stays HELD and then becomes UNDELIVERED with a note.
- Never send to a session the plan did not name, never write a card's `answer`, `options` or `title`, never push to the phone. Everything here stays on this machine.
- Never run this pass from a desk. A router may run it by hand while the task is not live: cards that target the router itself come back under `self`, and the router acts on them in its own turn.
