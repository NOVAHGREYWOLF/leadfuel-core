# wake (one watcher pass)

The owner clicks a card on the Router desk page, and before this nothing woke the router: he typed "answered" in its chat. This pass replaces that typing. It runs in a scheduled task of its own (`wake-on-answer`, Haiku, every 15 minutes), because only a Claude session can read the page's database and send a session a message, a session cannot message itself (measured: "refusing to send a message to the current session"), and a router that polled would spend a full-context turn on every tick. A plugin hook cannot do it (hooks fire only inside a session that is already running, and cannot call ArtifactData), nor can a plain local script (the page's database and session messaging are reachable only through Claude's tools).

**Four states, one pass.** `DELIVERED` only when the target's own transcript holds the card's token. A send that was queued or held for approval is `HELD` and is rechecked next pass, never resent. A failed send, or HELD or UNKNOWN past 120 minutes, is `UNDELIVERED` and gets a durable note on the Build Board. A pass that cannot read its inputs says `UNKNOWN`. A send is not delivered because it was sent.

## The pass
Pages: Router desk `https://claude.ai/artifact/LzmP6QcxmYh9TdvMMjS883` (collection `questions`); Build Board `https://claude.ai/artifact/A4uS9xn1emqupohdE4DUfV` (collection `router`). Script: `python "${CLAUDE_PLUGIN_ROOT}/scripts/wake_on_answer.py"`. Use PowerShell for any shell step (a scheduled run's Bash may lack tools on PATH).

1. **Tools**, one ToolSearch: `select:ArtifactData,mcp__ccd_session_mgmt__get_session,mcp__ccd_session_mgmt__send_message,mcp__ccd_session_mgmt__search_session_transcripts,mcp__ccd_session_mgmt__archive_session,mcp__scheduled-tasks__list_task_runs,mcp__ccd_session_mgmt__get_usage`.
2. **Self.** `get_session` with `self`: note your id S. The scheduled task runs in `auto` mode and that is expected (the routine's mode is set in the app and no session may change it): go on in `auto` or `bypassPermissions`. Only `default`, `acceptEdits` or `plan` stop the pass, with `WAKE-PASS UNKNOWN: not in auto or Bypass (mode=<mode>)` and nothing else done: a run in default mode cannot send (measured 2026-10-13), its send would wait for an approval nobody gives. **Until 0.1.15 this step also stopped `auto`, on an inference that was never measured; 11 passes in a row (2026-10-31) did nothing for that reason while 38 answered cards sat unrouted.** A send that `auto` refuses or holds is not a reason to stop: it is a result. Write the tool's whole text to `sent\<token>.txt` as step 7 says and let the judge call it HELD or UNDELIVERED.
3. **A fresh folder** W, new for this pass: `$env:TEMP\wake-on-answer\<UTC yyyyMMddTHHmmss>`, with `work\sent` and `work\seen` inside. Never reuse one: the script counts files.
3b. **PHONE BRIDGE** (0.1.25; the owner's G39: his Router desk cards reach his phone and his answer comes back to the desk that asked). **Off unless he switched it on.** The pass sends something off this machine only here, only through `phone_cards.py`, and only when `PHONE_CARDS_PUSH=1` (and `PHONE_CARDS_URL`, `PHONE_CARDS_TOKEN` and `PHONE_CARDS_ACCOUNT` are set). It runs before step 4, so an answer it writes is routed in this same pass. Never print, read back or write down the token or the account. Its folder is `W\phone`.
   - **Gate.** `python "${CLAUDE_PLUGIN_ROOT}/scripts/phone_cards.py" status`. If it prints `PHONE-CARDS OFF: <names>`, **do nothing else in this step and go to step 4: the pass is exactly what it was, nothing is read for the phone and nothing is sent.** `PHONE-CARDS UNKNOWN` (exit 2): skip the step and carry that line to the end line. Only `PHONE-CARDS ON` goes on.
   - **Read.** ArtifactData `query` on the Router desk, collection `questions`, the same query as step 4 (`{"where": [["routed", "==", null]], "limit": 500}`), `out_dir` W\phone\cards. Note its count N and keep its lines (they carry each card's version). If it fails, the line is `PHONE-CARDS UNKNOWN: cannot read the questions collection` and the rest of this step is skipped.
   - **Plan.** `python "${CLAUDE_PLUGIN_ROOT}/scripts/phone_cards.py" plan --cards W\phone\cards\questions --count N --out W\phone\payload.json`. It keeps the cards nobody has answered, drops the asking session's id and every key outside the card shape, and sets `complete` true only when it read all N cards (a short or cut-off read never withdraws a card from the phone).
   - **Push.** `python "${CLAUDE_PLUGIN_ROOT}/scripts/phone_cards.py" push --payload W\phone\payload.json --out W\phone\resp.json`. This is the one call that leaves the machine: one POST to the owner's hub. `PHONE-CARDS OFF` means nothing was sent: skip to step 4. `PHONE-CARDS UNKNOWN` (exit 2) means the hub's answer could not be read: apply no answer, skip the rest of this step, and never read it as "no answers".
   - **Apply.** `python "${CLAUDE_PLUGIN_ROOT}/scripts/phone_cards.py" apply --answers W\phone\resp.json --cards W\phone\cards\questions --count N --out W\phone\out`. The first run prints `PIN cards=...` and `NOT WRITTEN (no version to pin)`: write `W\phone\versions.json` as `{"<card id>": <version>}` for exactly the cards on the `PIN` line, from the Read lines, and run the same command again with `--versions W\phone\versions.json`. A phone answer lands only on a card the desk has not answered: if the desk answered first the script prints `CONFLICT`, writes nothing, and the desk's answer stands. `PHONE-CARDS HOLD` means the read was not provably whole: nothing is written or acknowledged for that card.
   - **Write.** If `W\phone\out\batch.json` is not `[]`: one ArtifactData `batch` on the Router desk whose `writes` are its entries exactly as written (each points at a card file and is pinned with `if_version`; on a version conflict nothing is written for that card and it is not acknowledged: next pass the desk's answer is a `CONFLICT`).
   - **Ack.** Only after that batch returned: `python "${CLAUDE_PLUGIN_ROOT}/scripts/phone_cards.py" ack --ids <the ACK-NOW ids and the ACK-AFTER-BATCH ids whose write succeeded, comma separated> --out W\phone\ack.json`. Never acknowledge a card whose write failed or was not made: the hub keeps its answer and hands it back next pass. An `ack` that prints `PHONE-CARDS UNKNOWN` is harmless and is retried next pass (`apply` sees the answer already on the card and does not write it twice).
   - Then step 4. Its query reads the cards afresh, so a phone answer just written is an answered, unrouted card to every step below, and goes to the session that asked exactly as if he had clicked it on the page (the card also says `answered_via: "phone"`). Keep the bridge's last line, `PHONE-CARDS applied=… conflict=…`, for step 11.
4. **Read the cards.** ArtifactData `query` on the Router desk, collection `questions`, query `{"where": [["routed", "==", null]], "limit": 500}`, `out_dir` W\cards. The page writes `routed: null` on every answer and every note, so this is exactly the unrouted set (measured 2026-10-14: 23 cards, the answered census cards among them). Note the count N the result reports and keep its lines: they carry each card's version. If the query fails, end with `WAKE-PASS UNKNOWN: cannot read the questions collection`.
5. **Read the live router.** ArtifactData `get` on the Build Board, collection `router`, doc `current`, `out_dir` W\board. Never read it inline: it is about 260 KB. Read it every pass: the router rotates (it did during the proof) and the script follows `session_id`.
6. **Plan.** `plan --cards W\cards\questions --count N --router-current W\board\router\current.json --sessions-dir "$env:APPDATA\Claude\claude-code-sessions" --self S --out W\plan.json`. The script reads the desktop app's own session folder to find the router a card's `asker` names (`ROUTER #114 · app brain link`), or its live successor in that project, because no card carries `asker_session` and `router/current` is one router for the whole estate (measured 2026-10-31: it named a retired router while twelve project routers were asking). Since 0.1.18 an asker that is exactly one live session's title (`WATCH · desk archival analysis part 2`) reaches that session, and **an asker that names `ROUTER #N` when the store is readable and no live router has that number or project is NO TARGET**: the card is judged UNDELIVERED with a note on the Build Board, and is never sent to `router/current` (measured 2026-10-31: that named a retired router of another project). A pass of 2026-11-01 00:08Z found that a send to an idle router came back `no sign of starting within 20s` four times out of five and none of the five messages was in any target's transcript 80 minutes later: treat `undelivered` as real, do not assume the text arrives late. It sends a card the owner answered more than 48 hours ago to nobody and lists it as `stale` (he relayed it by hand long ago), and it puts at most 10 cards and 7,000 characters in one message so that you can send the text unchanged; the rest wait for the next pass. It prints one `SEND` line per target (at most five), one `RECHECK` line per held or unknown card, a `PIN cards=…` line, or `WAKE-PASS nothing to deliver`; in that case go to step 10. A `WARNING: no readable session store` line is not a failure: those cards went to the live router. `WAKE-PASS UNKNOWN` (exit 2): end with that line. Write `W\work\versions.json` as `{"<card id>": <version>}` for exactly the cards on the `PIN` line, from the step-4 lines.
7. **Send**, for each `SEND to=<id> token=<token> ... message=<file>`: Read the message file and send its text, unchanged, with `mcp__ccd_session_mgmt__send_message` to `<id>`. Write the tool's whole result, error text included, to `W\work\sent\<token>.txt`. Only after the send has returned, `search_session_transcripts` with query `<token>` and `limit` 10, and write its whole output to `W\work\seen\<token>.txt` (`No matching sessions found.` included). Never issue the two calls together: a search raced against its send finds nothing (measured), and the card waits a pass as UNKNOWN. Send nothing else to anyone.
8. **Recheck**, for each `RECHECK ... token=<token>`: `search_session_transcripts` with query `<token>`, output to `W\work\seen\<token>.txt`. Never resend.
9. **Judge and write.** `judge --plan W\plan.json --work W\work --out W\out`. Then one ArtifactData `batch` on the Router desk whose `writes` are the entries of `W\out\batch.json`, exactly as written (each points at a card file and is pinned with `if_version`; on a version conflict write nothing for that card: the next pass takes it again). If `W\out\fallback.json` is not `{}`: ArtifactData `get` Build Board `router/wake_undelivered` with `out_dir` (missing is fine), then `update` it with `file_path` W\out\fallback.json, pinned to the version you read (a `set` with no pin only when it did not exist).
10. **Tidy.** `list_task_runs` for `wake-on-answer`, `limit` 20. Archive each run that is not S, not archived, and has status `succeeded` or `failed` (never `running`), one at a time with `archive_session`. Never archive anything else.
10b. **Resume sweep** (0.1.20; owner, 2026-10-31: "i shouldnt have to keep approving things"). A session that died on a usage limit (`You've hit your weekly limit, resets 2pm (America/Tijuana)`) stays dead until someone types "keep going"; the owner typed it into about a dozen after the reset of 2026-10-31. After the Tidy step, call `get_usage` and write its whole JSON to `W\usage.json`; count the sends this pass made (step 7) as K; then `python "${CLAUDE_PLUGIN_ROOT}/scripts/resume_sweep.py" plan --sessions-dir "$env:APPDATA\Claude\claude-code-sessions" --usage W\usage.json --state "$env:LOCALAPPDATA\leadfuel-way\resume_sweep_state.json" --self S --already-sent K --out W\sweep.json`. It prints one `NUDGE to=<id>` per stranded session whose limit has reset and that nobody has touched since (store `error` matches "hit your .* limit", `lastActivityAt` no later than `errorAt` plus two minutes, not archived, not a run of another routine, `errorAt` within 72 hours), at most 8 and never more than the ten sends a session may make before messaging pauses (K counts), and only while `get_usage` shows no window at 100%. `RESUME-SWEEP FULL` or `UNKNOWN` means send nobody. For each `NUDGE`, `mcp__ccd_session_mgmt__send_message` to `<id>` with exactly `limit reset, keep going`; then `resume_sweep.py record --plan W\sweep.json --state <the same file> --sent <ids whose send did not return an error>`, so the cooldown (60 minutes, three nudges for one error) holds. A row it lists as unknown (reset time unreadable) is never nudged. Never change a permission mode; a send the app holds is a result, not a reason to retry.
11. **End** with the judge's last line (`WAKE-PASS DELIVERED=… HELD=… UNDELIVERED=… UNKNOWN=…`), or the step-6 line, then the sweep's last line (`RESUME-SWEEP nudge=...`), and when step 3b ran, the bridge's last line (`PHONE-CARDS applied=… conflict=…`, or the `PHONE-CARDS UNKNOWN` line that stopped it; nothing when it printed `PHONE-CARDS OFF`). Ids and counts only.

## What a card carries afterwards
- `wake`: `{state, at, to, why, delivery, message_id, first_sent_at, sends, answered_at, note_at, by}`. The token is never written to a card: a router reading the card would otherwise carry it in its own transcript and a message that never arrived would look delivered.
- `routed` (only when DELIVERED): `{at, by: "wake-on-answer", to, note}`. The page then shows the owner that his answer was picked up. The session that acts writes what it did in `routed.note`.
- A card the owner answers again, or adds a note to, gets `routed: null` from the page and a new `answered_at` or `note_at`, so the next pass sends it again.
- A card answered on the phone (step 3b) carries the page's own click fields (`answer`, `answered_at`, `note` and `note_at` when he wrote one, `routed: null`) plus `answered_via: "phone"`, so every later step treats it like a click.

## Who is the target
`asker_session` when it is a full `local_` id; else a full `local_` id inside the `asker` text; else the live router, `router/current.session_id` on the Build Board. A row id such as `intelligence/local_8e471cfd-1` is not a session. A router that wants a desk woken directly puts that desk's id in `asker_session` when it posts the card, and only for a desk under 300k tokens (`leadfuel-way:router`, "Waking").

## Never
- Never change any session's permission mode to get a message through (the owner's standing rule). A held message stays HELD and then becomes UNDELIVERED with a note.
- Never send to a session the plan did not name, never write a card's `options` or `title`, and never write a card's `answer`, except the owner's own phone answer through `phone_cards.py apply` (step 3b), which writes it only to a card the desk has not answered.
- Everything here stays on this machine. The one thing that leaves it goes only through `phone_cards.py` (step 3b) and only when `PHONE_CARDS_PUSH=1`; with it unset the pass is unchanged and nothing is sent. Never print the token or the account.
- Never run this pass from a desk. A router may run it by hand while the task is not live: cards that target the router itself come back under `self`, and the router acts on them in its own turn.
